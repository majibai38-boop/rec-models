**推荐模型 Benchmark 平台实施计划**

创建日期：2026-10-28。设计依据：[平台方案](recommendation-benchmark-platform-proposal.md)。当前状态：仅完成方案持久化，以下工程任务均未开始。建议按 M0 → M1 → M2 → M3 → M4 推进，每项完成后记录实现提交、验证方法、证据位置和限制。

本计划的 6–8 周估算以两名工程师、兼职性能/运维支持、可访问的 GPU/NPU 节点为前提。复杂算子移植、采购和多机训练不计入首期。日期是规划假设，不是已经安排的执行承诺。

**首期范围固定为单卡、FP32、eager、共同实现轨和固定步数 train step。** 模型选 DeepFM 或 DCNv2、小型 DLRM、DIN；以第一个小型 DLRM 的双侧闭环为优先。每项能力经验证后再对外声明支持。混合精度、编译、后端优化、服务推理、训练达标时间和多卡多机进入后续迭代。

| 里程碑 | 建议窗口 | 依赖 | 完成标志 |
|---|---|---|---|
| M0：执行条件与协议 | 第 1 周 | GPU/NPU 节点与数据访问条件 | 冻结首个模型、环境和可比测量协议 |
| M1：本地双后端运行内核 | 第 2 周 | M0 | 同一配置在两端独立运行并产出标准结果 |
| M2：远程执行闭环 | 第 3 周 | M1 | 提交实验后自动完成分配、运行、上传与恢复 |
| M3：Web / Skill 与诊断 | 第 4–5 周 | M2 | 同一 API 驱动两类入口，可下钻原始证据 |
| M4：可信评测与回归 | 第 6–8 周 | M3 | 三个模型、真实数据子集、质量门槛和重复实验通过验收 |

**M0：执行条件和实验协议。** 先补齐实际设备信息，再选择软件组合。设备不可访问时可以推进 schema 与假执行器，但不能标记硬件验收完成。

- [ ] M0-01：记录 GPU/NPU 型号、数量、CPU 架构、内存、网络/拓扑、OS、驱动、固件、现有调度系统和访问方式。
- [ ] M0-02：盘点当前提交与工作区差异，确认已有分析、规格目录和 UI 能力；明确哪些可复用代码需要另行合入。
- [ ] M0-03：选定双方支持的 Python/PyTorch 与 CUDA 或 CANN/torch_npu 组合；形成环境配方、兼容性依据和镜像 digest。
- [ ] M0-04：确定小型 DLRM 定义、输入生成器、embedding 表/访问分布、初始 checkpoint、optimizer 和数值容差。
- [ ] M0-05：定义版本化 `BenchmarkSpec / RunManifest / Metric / Artifact`，区分 workload 条件指纹和环境指纹。
- [ ] M0-06：冻结 fixed-steps、预热、pilot、同步、计时范围、重复实验、状态恢复和质量门槛；明确 train step 包含哪些操作。

验收：配置可序列化、校验、展开和重新读取；不支持的组合有明确原因；计划中没有未解析的关键版本或硬件假设。两端节点健康与环境 smoke test 留有记录。

**M1：建立可独立验证的运行内核。** 建议新增 `benchmark_core` 和 `benchmark_catalog`，以 CLI 验证完整数据流后再接 UI。

- [ ] M1-01：实现模型 adapter 与能力声明；输入和初始训练状态支持冻结与重放。
- [ ] M1-02：实现 CUDA / Ascend backend 的环境探测、设备选择、同步、内存统计和独立 profiler 接口。
- [ ] M1-03：实现实际执行路径的正确性检查，覆盖输出、loss、梯度或参数更新；不允许静默 CPU fallback。
- [ ] M1-04：实现 pilot 后冻结双方共同步数 N、共同预热和输入序列；每次重复恢复模型、optimizer、RNG 与数据游标。
- [ ] M1-05：实现原始测量、有效样本数、墙钟吞吐、分布和重复汇总；区分 device-only 与 end-to-end。
- [ ] M1-06：实现独立 profiling 重放，保存采集配置、逻辑步骤偏移、rank/device/PID/step 及原始文件。
- [ ] M1-07：提供配置校验、运行、状态/结果读取的 CLI，输出结构化错误和标准产物清单。

验收：同一 workload 可在真实 GPU/NPU 上执行；计时正确等待设备完成；各次重复的受控起点与工作量可核对。profiler 运行与正式测量分开，原始结果能复算汇总值。没有真实硬件时只记录软件验证结果。

**M2：增加持久控制面与节点 Agent。** 建议新增 `benchmark_service`，模型执行与现有 profiling 分析 worker 分离。

- [ ] M2-01：建立 PostgreSQL 中的实验、run、attempt、节点、设备租约、指标和产物记录；提供迁移与恢复方法。
- [ ] M2-02：实现 Agent 身份、节点准入、心跳、设备匹配和原子独占租约。
- [ ] M2-03：按已注册镜像和校验参数启动容器，回传阶段与日志，限制运行时间和资源。
- [ ] M2-04：支持幂等提交、取消、基础设施错误有限重试；每次重试有独立 attempt。
- [ ] M2-05：处理节点断线和控制面重启；旧容器状态未确认前不得在同设备重派，使用 fencing 防止过期执行者修改状态。
- [ ] M2-06：产物先落盘、hash 校验后上传并原子发布；不覆盖历史结果，不将 trace 存入数据库。
- [ ] M2-07：提供统一的校验、创建、提交、状态、取消、指标、对比和产物 API；多人场景配置用户/项目授权。

验收：关闭客户端后实验继续；重复提交不会重复占卡；取消能释放资源；断线、进程失败、部分上传和控制面重启均有明确结果与恢复证据。

**M3：统一用户入口并连接现有分析。**

- [ ] M3-01：扩展现有 Vue / ECharts 工作台，增加环境设备、模型数据、实验创建与运行详情页面。
- [ ] M3-02：展示真实阶段、日志、失败原因和产物；未知阶段时长不伪造完成百分比。
- [ ] M3-03：增加对比条件校验、吞吐/延迟/内存视图、质量状态、波动和环境差异展示。
- [ ] M3-04：将符合输入合同的 GPU/NPU profile 交给现有分析引擎，记录分析版本与范围并链接到证据页。
- [ ] M3-05：分开记录 benchmark、quality、profile 和 analysis 的状态；profiling 失败不删除有效实测结果。
- [ ] M3-06：新建 `rec-benchmark` Skill，通过同一个 CLI/API 校验配置、提交任务、读取结果并返回 Web 链接。
- [ ] M3-07：保持 `gpu-npu-profiling` 的分析职责；workload_modeler 预测独立展示，不进入实测排行榜。

验收：Web 与 Skill 提交相同配置得到相同配置指纹；入口不自行计算另一套统计口径；实验结果可追溯到 manifest、原始测量、日志和选定分析事件。

**M4：形成可信的首期 Benchmark Suite。**

- [ ] M4-01：完成三个代表模型的 adapter、后端能力表和固定配方。
- [ ] M4-02：登记公开真实数据子集的来源、split、预处理、特征词表、输出 hash、候选集/负采样协议。
- [ ] M4-03：分别验证数值一致性和业务质量；质量失败保留诊断但不进入通过门槛的比较榜单。
- [ ] M4-04：执行至少 5 次独立重复的初始稳定性实验，保留原始值、中位数与波动；根据实测噪声校准回归策略。
- [ ] M4-05：验证比较条件，不同协议仅并排展示；正式成绩使用墙钟测量，不使用 kernel 时长求和或预测值替代。
- [ ] M4-06：演练设备重复分配、节点失联、取消、OOM、数值错误、产物损坏与采集缺失；记录恢复结果。
- [ ] M4-07：补全部署、配置、添加模型、添加环境、故障定位和结果解释文档，交付完整演示实验。

验收：从任一入口一次提交，即可完成两端执行、测量、结果比较与证据下钻。三模型的支持条件和未支持项清楚列出，重新运行能恢复被冻结的工作负载与环境选择。

**后续工作按独立能力验收，不计入首期完成条件。**

- [ ] F-01：混合精度与编译模式，验证实际测量路径及其质量/稳定性。
- [ ] F-02：GPU TorchRec/FBGEMM 与 NPU Rec SDK 优化轨，固定各自实现及版本，不与共同实现轨混排。
- [ ] F-03：推理服务与 LoadGen，明确请求入口、到达率、并发、排队、batch 和尾延迟样本量。
- [ ] F-04：训练达到目标质量，记录完整预算、评价周期与失败/未达标情况。
- [ ] F-05：多卡多机、embedding 分片、通信和拓扑调度，增加整组资源分配与失败清理。
- [ ] F-06：HSTU / DLRMv4 等序列推荐模型；固定正式与缩小 workload 的不同身份。
- [ ] F-07：按需求接入对象存储、集群调度、遥测和 MLflow；保持任务状态与测量结果的唯一事实来源。

**进度维护约定。** 已完成事项使用 `[x]`，并在下表增加证据。调整实现范围、指标语义或依赖时，同步修改方案与计划，记录原因。硬件能力未验证时不得因接口或 mock 测试通过而勾选验收完成。
