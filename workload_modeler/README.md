# Workload Modeler：单机性能建模工具

独立于现有 `profiling_web` 的单机 MVP（v0.4），复用仓库 `profiling_tools` 的 Trace 解析和 kernel 归属逻辑。不修改原始采集数据或外部 workload 工作簿。

## 与 Profiling Workbench 的区别

| | Workload Modeler（本服务） | [Profiling Workbench](../profiling_web/README.md) |
|---|---|---|
| 使用场景 | 单侧采集的画像、迁移初筛与假设下性能预测 | GPU/NPU 双侧采集的实测性能比较 |
| 必需输入 | GPU Trace；或 NPU Trace + 明细；或仅 NPU 明细 | GPU Trace + NPU Trace + NPU 明细 |
| 重点操作 | 管理芯片/平台、选择源与目标、编辑估算假设 | 对齐 kernel、查看类型/整体对比、诊断覆盖率、人工关联 |
| 性能比 | 源实测时间 / 目标预测时间 | GPU 实测时间 / NPU 实测时间 |
| 默认端口 / 数据目录 | 8770 / `workload_modeler/data/` | 8000 / `profiling_web/data/` |
| 输出 | 网页结果、CSV、JSON、经验场景 JSON | Excel、CSV、Markdown、JSON |

两套服务独立启动，任务不自动互通；仅复用解析能力和界面主题。单侧预测无需运行 Profiling 服务。取得目标设备实测后，可用 Profiling Workbench 验证估算结果。

## 启动

在仓库根目录执行（Python 3.10+）：

```powershell
python -m venv workload_modeler/.venv
workload_modeler/.venv/Scripts/python -m pip install -r workload_modeler/requirements.txt
workload_modeler/.venv/Scripts/python -m workload_modeler --port 8770
```

Linux / macOS：

```bash
python3 -m venv workload_modeler/.venv
workload_modeler/.venv/bin/python -m pip install -r workload_modeler/requirements.txt
workload_modeler/.venv/bin/python -m workload_modeler --port 8770
```

无需 Node.js、pnpm 或前端构建。部署时保留整个仓库，尤其是复用的 `profiling_tools/` 和 `web_shared/`。已有 Profiling 虚拟环境时，也可以复用它：

```powershell
.\profiling_web\.venv\Scripts\python.exe -m pip install -r workload_modeler/requirements.txt
.\profiling_web\.venv\Scripts\python.exe -m workload_modeler --port 8770
```

浏览器访问 http://127.0.0.1:8770 。默认仅监听本机、无需令牌；局域网访问可配置监听地址和认证模式，见文末。数据默认存储在 `workload_modeler/data/`，可用 `--data-dir` 指定。不要对同一数据目录启动多个服务。停止服务后备份整个数据目录即可保留任务、规格和结果。

后续启动只需执行环境对应的最后一条命令，按 `Ctrl+C` 停止。自定义数据目录示例：

```powershell
workload_modeler/.venv/Scripts/python -m workload_modeler --port 8770 --data-dir D:/workload-data
```

上传、数据库、任务结果和日志属于本机运行数据，不随源码提交。恢复备份时先停服务，再使用 `--data-dir` 指向已恢复的目录；不要把正在运行的 SQLite 数据库单文件复制作为完整备份。仓库中的 `profiling_web/Dockerfile` 仅部署 Profiling，本服务当前使用 Python 直接启动。

## 使用流程

界面与 Profiling Workbench 共用浅色青绿主题、左侧任务栏、页签、表格和结果卡片；「模型分析 / 芯片规格 / 平台配置」均从左栏进入。共用样式位于仓库 `web_shared/theme.css`，部署时需保留该目录。升级本次界面后重启 Workload 服务并刷新页面即可，无需前端构建；历史数据和分析口径不变。

1. 在「芯片规格」中查询、新建或修改规格。默认使用表单，单位固定；填写数值、证据类型、来源和稠密口径。未知值留空，不能填零占位。高级用户可切换 JSON；支持单条 JSON 导入预填和导出，导入后需明确保存才生效。
2. 在「平台配置」中从下拉列表选择明确的芯片和版本（含历史版本），并填写 CPU、内存、软件版本、拓扑等条件。芯片修改不会自动升级平台引用。
3. 选择输入类型、源平台和目标平台，再选择文件：GPU `trace.json/json.gz`；NPU 可选择 Trace 和 `kernel_details.csv`，也支持仅 CSV。无需单独点击上传；点击主按钮时自动上传，未新建任务时自动创建。仅选择文件不会开始上传。
4. 「预检查范围」是独立开关，默认开启。开启时，主按钮先执行「上传并预检查范围」，列出 CPU PID、Step、设备；确认范围后，再点击「生成画像与预测」。关闭时，填写已知 PID/Step/设备后点击「上传并分析」，跳过独立预检查和重复解析。Step必须明确填写，或者主动勾选全采集范围；PID/设备留空只允许唯一候选，歧义会报错，不自动取最繁忙项。CSV-only限定Step仍要求明细提供Step ID。
5. 填写工作负载条件，检查「整体经验估算」假设（默认开启）及精细预测的效率、启动开销、精度模式，再运行分析。
6. 顶部直接显示设备整体与整步经验倍率，并分别显示精细预测覆盖率与局部倍率。默认保留算子折算表；「整体经验估算」显示保守/基准/乐观耗时、倍率、互斥类别与折算依据。「画像与整步」保留画像和严格整步条件；「风险与假设」按耗时汇总精细模型缺口。
7. 已完成任务可点击「调整经验假设」→「预览整体估算」，无需重新解析Trace；可导出当前经验场景JSON。预览不会改写原任务，刷新恢复保存/默认假设。若要保存完整新分析，使用「复用输入」，可预检查或确认原范围后直接运行。支持任务改名、取消和历史结果查看。
8. 任务、芯片规格和平台均支持「移入回收站」与恢复。任务在左侧勾选「回收站」，规格/平台在对应页面勾选「回收站」。任务支持名称搜索和每页50项分页；规格/平台支持名称、厂商、CPU和备注搜索。

已完成/运行中任务的输入表单只读（已完成任务的经验假设预览除外）；已完成任务会恢复展示该次 PID/Step/设备范围。任务名称仍可通过「修改名称」调整。单条 JSON 只传递条目本身，不包括任务数据或私有访问令牌。

预检查和上传过程中保留当前配置；切换任务会清空尚未上传的文件选择，避免误传到另一任务。成功上传的文件不重复上传，后续文件失败时可重试；选了新文件必须重新预检查（若开关开启）。已有输入不必重新选择。失败任务可修正范围直接重试，或替换文件，不再强制先预检查。未提交的表单草稿仅保留在当前页面内，刷新会丢失。

快速体验：上传 `examples/gpu_trace.json`，选择 GPU、源 L20 和目标 950PR、Step `ProfilerStep#1`。这是两个 FP32 Add 调用的合成示例，不是硬件实测。源、目标均选择 L20 时，默认基准假设下设备倍率为 1。

NPU CSV 示例：新建任务，仅上传 `examples/kernel_details.csv`，输入类型选择 NPU，源/目标平台均选 950PR 32，预检查后选择 Step 1。Add/Relu 可建模时间为 30 μs，MatMul 的 50 μs 因缺少转置/布局语义而保留未知；覆盖率应为 37.5%。这些数字仅用于功能回归，不是实测性能。

### 删除与恢复

- 「移入回收站」仅隐藏条目，不删除上传文件、结果、历史规格版本或分析快照，也不释放磁盘空间；回收站数据仍计入10GiB软配额。本版没有永久清空入口。
- 上传、预检查、分析中的任务不能删除；后台进程尚未退出时也拒绝删除。已删除任务必须先恢复，才能查看、下载、改名、复用输入或重跑。
- 芯片被任一有效平台（包括固定旧芯片版本）引用时不能删除。先修改平台引用，或将相关平台移入回收站，再删除芯片。恢复顺序为先芯片、后平台。
- 修改、删除、恢复规格/平台均校验版本，防止覆盖另一页面刚保存的变更；历史版本和分析结果始终使用原快照。
- 已删除平台不能用于新分析；旧结果仍可查看。网页保留已删除平台的历史快照标签，不悄悄替换为其他平台。
- 升级服务时，旧SQLite数据库自动增补回收站字段；新的内置设备只安装一次，不覆盖用户修改，也不会在重启时复活已删除条目。升级前建议停止服务并备份数据目录。

这些回收站语义适用于 Workload。Profiling Workbench 原有「归档/永久删除」流程未改动，不要将两个工具的删除方式混淆。

### 新增设备与规格口径

详见 [设备来源与口径](docs/device_presets.md)。新增7种芯片及其单设备平台：A100 40/80GB PCIe/SXM和950DT 28/32/36 Cube，原L20、950PR条目保持不变。

矩阵算力使用稠密峰值，不混用稀疏峰值，也不把Cube与Vector峰值相加。芯片卡片中的「规格来源与口径」可直接展开查看资料。A100主机信息因原表未明确SKU而不自动套用；950DT 28 Cube参考平台记录原工作簿主机配置，其余未确认参数留空。950DT显存容量没有明确的核数档位对应关系，仍为未知。

### 元数据与诊断边界

- NPU 的 `32,128;32,128` / `FLOAT;FLOAT` 等 CSV 写法经原解析器规范化，并保留原字段。CPU owner 已存在时不以 kernel 字段替换 CPU 输入，更不会把它们冒充 GPU kernel 参数。
- CSV-only 的 MatMul 类别没有完整 CPU 转置/布局语义，不能仅按名字套用 `aten::mm` 模型；必须补充证据或人工校准。已知逐元素输出 Shape/dtype 与假设冲突时也停止解析预测。
- 原因桶覆盖全部未建模调用，每项只计入一个当前阻止原因；顶部热点仅显示前 20 项。修复一个原因后可能暴露下一个原因，桶占比不是保证可恢复的覆盖率或优化收益。
- 缺规格、估算未确认、稠密口径、精度模式、元数据、未支持算子、广播/Shape、实现语义及内存/通信分别给出建议。原因汇总耗时与未建模总耗时进行守恒检查。
- `c10::Half` / `c10::BFloat16` / `torch.float16` 等浮点别名在本工具内统一，原始字段保留。Scalar/TensorList参数单独提示语义未建模，不当作未知Tensor精度；未支持算子直接说明模型缺口。
- v0.4 新结果为 schema 4，JSON含三层 `assessment` 和独立的 `empirical`。旧结果网页可基于保存的调用补充默认经验预览（明确标注），不会改写历史预测或原下载件；当前经验场景可单独导出。dtype规范化可能改变签名，请不要机械沿用旧校准签名。

### 整体经验估算（旧workload式大类折算）

这是独立的粗估模式，不把精细预测0%覆盖率当作拒绝输出的门槛，也不把经验结果冒充精确预测。默认的FP16档位、矩阵50%计算/50%访存、Vector按带宽等均是可编辑假设，不是从计数器证明的bound结论；适用于快速筛选与敏感性分析，不等于目标实测或直接证明“亲和昇腾”。

设备活动按以下顺序**互斥归类**：内存活动、通信活动先独立；计算kernel小于5μs归为短kernel；其余按FA/HSTU/混合、Cube、Vector、Unknown归类。Cube的时间按用户比例拆成计算/访存两部分，不重复计时。短kernel判断以单个事件为准，不是CPU调用的总时长。

| 类别 | 默认基准源/目标倍率 | 保守 / 乐观 |
|---|---|---|
| 矩阵计算 | 目标矩阵峰值 / 源矩阵峰值；默认FP16→FP16 | 基准×0.7 / ×1.3 |
| 矩阵访存、Vector | 目标带宽 / 源带宽 | 基准×0.7 / ×1.3 |
| FA/HSTU/混合、内存活动、通信 | 1（中性假设） | 0.7 / 1.3 |
| 短kernel | 1（中性假设） | 0.5 / 1.3 |
| 未知类别 | 1（中性假设） | 0.5 / 1.5 |
| 缺少对应规格 | 1（中性假设） | 0.7 / 1.3 |
| Step非设备忙碌时间 | 1（保持不变） | 1 / 1 |

所有倍率须为正，且保守≤基准≤乐观。可选择FP16/BF16/FP32/TF32/HF32规格档位、直接覆盖矩阵/带宽基准倍率、调整类别倍率和短kernel阈值。经验模式允许使用稠密口径未确认或估算规格，但显式警告；不会修改硬件库或放松精细模型的证据约束。缺规格始终留空，只有经验假设使用显式兜底倍率。

```text
目标设备时间 = Σ(源类别时间 / 类别倍率)
设备整体倍率 = 源设备时间 / 目标设备时间
耗时减少% = (1 - 目标时间 / 源时间) × 100

目标忙碌时间 = 源Step内忙碌时间 × 目标设备求和时间 / 源设备求和时间
目标Step = 目标忙碌时间 + (源Step - 源Step内忙碌时间) / 间隙倍率
Step倍率 = 源Step / 目标Step
```

**不对倍率做耗时加权算术平均。** 多流Step采用整体重叠比例不变的粗估，不是关键路径/调度仿真；间隙不能直接认定为CPU开销。CSV-only或缺Step窗口时仍输出设备估算，不编造Step。保守/乐观只是参数敏感性范围，不是统计置信区间，也不是可靠上下界。数据很不完整时，应优先验证占比高的类别假设。

新任务的经验配置保存在 `config.request.empirical`，结果在 `empirical`。旧任务加载时只生成默认预览。`POST /api/jobs/{id}/empirical-preview` 接收 `EmpiricalAssumptions` 对象（默认值见 `/api/meta`），复用历史输入、硬件快照及调用数据，返回经验估算与来源信息；不改写文件。独立导出的经验JSON包含当前假设和原任务快照，原 `result.json` 下载仍保持不变。

### 三层结论

1. **画像与亲和性初筛**不依赖性能建模覆盖率。Cube/Vector占比分母为全部计算kernel时间，包含Unknown；未知项不重新分配。Cube或Vector超过50%时提示主导路径。目标解析模型访存主导时间超过全部Cube时间70%时提示矩阵访存风险；未建模Cube时间以可能范围显示。规则是排查启发，不代表硬件实测或已经验证的亲和性。
2. **已建模部分预测**只比较已覆盖子集，始终显示覆盖率、未覆盖源时间和局部倍率。缺规格不会补成倍率1，未知dtype不会默认TF32。
3. **整步性能预测**继续检查完整覆盖、单流、重叠、Step边界及固定间隙假设。不满足时列出原因，仍保留前两层结论。

短kernel定义为单个计算kernel耗时小于5μs，不等同小Shape或已确认启动受限。FA/HSTU按调用名识别，其时间与Cube/Vector分类交叉，不能相加。Step未被设备活动覆盖的时间使用窗口内活动并集计算，不能直接认定为CPU调度开销。初筛阈值仅为经验规则，随结果保存；不使用旧工具的固定MNK访存阈值和缺失规格兜底规则。

## Trace Shape 参数量画像

新分析在「画像与整步」顶部显示参数量候选：稠密权重、Embedding表、候选合计和待确认矩阵右输入元素数。明细显示算子、角色、Shape、dtype、模块、元素数、调用次数和去重依据；完整数据随 `result.json` 的 `profile_summary.parameters` 导出。旧任务需「复用输入」重新分析。

Linear、卷积、Embedding及支持的归一化CPU算子按权重/偏置入参位置取Shape乘积；仅分析所选PID、Step及设备kernel关联的CPU调用与祖先，跳过外层权重算子的内部重复实现。重复Step不按调用次数累计。同模块（若有）、算子族、角色、Shape和dtype的候选合并。没有模块信息时仅按Shape等字段去重，因此同Shape的不同层可能低估，共享权重、跨算子或多精度副本可能高估。这是候选规模，不是精确总参数量，也不是上下界。

Embedding使用完整表的Shape，包含未访问的行；无法从索引Shape确定唯一激活行数，也不能由此判断梯度是否稀疏。普通mm/addmm/matmul/bmm可能是激活间运算，右输入规模独立列为待确认项，不加入参数候选合计。未采集分支、融合或外置权重、无Shape、CSV-only等场景保留未知；不把未识别显示成0。精确模型参数量需模型或state_dict提供唯一权重及共享关系。此画像不改变现有性能预测。

## 指标与预测口径

- **设备总时间**：计算 kernel、内存活动和通信活动 Duration 求和；不是迭代墙钟时间。
- **设备忙碌时间**：活动区间并集。并发时可小于 Duration 总和。
- **Step 时间**：CPU Trace 中唯一 Step 标记的墙钟时长。CSV-only 不推断它。
- **NPU 分类**：`aicore_time=0` 为 Vector，正值为 Cube，缺失为 Unknown。混合核仍按此约定分类，并保留 aic/aiv 原始值；分类不是流水利用率。
- **GPU 分类**：根据逻辑 CPU 算子语义得到 Cube-like/Vector-like/Mixed/Unknown，只作参考，不能等同硬件计数器。
- **分类时间占比**：分母仅计算 kernel 时间，含 Unknown，不包含通信和内存活动。
- **建模时间覆盖率**：已建模源活动时间 / 全部源设备活动时间。未知时间单列，不补成倍率 1。
- **性能倍率**：源耗时 / 目标预测耗时。GPU→NPU 时才是 GPU/NPU；大于 1 表示目标在该假设下更快。

解析模型（单位换算在代码中完成）：

```text
解析时间 = kernel数量 × 启动开销 + max(FLOPs / 有效算力, 逻辑字节 / 有效带宽)
目标预测时间 = 源实测时间 × 目标解析时间 / 源解析时间
有效算力/带宽 = 对应峰值 × 用户设定效率
```

默认计算效率 0.6、带宽效率 0.7、每 kernel 启动项 3μs 均为**场景假设，不是实测校准**。假定两侧实现、逻辑流量与启动次数不变。逻辑字节不是 DRAM 实际访存量。保守/基准/乐观场景分别将目标效率乘以 0.7/1/1.3（上限 1）；这个范围不是统计置信区间，也不包含全部实现误差。

矩阵峰值必须明确 `dense:true`。L20 内置矩阵数据的稠密/稀疏口径未确认，默认不参加矩阵预测。FP32 矩阵须选择 FP32/TF32/HF32 模式；两侧不同模式还须确认精度策略可比较。估算规格默认不参与预测。

严格整步预测仅当整步条件满足并勾选固定间隙场景时：`目标Step = 源Step - 源设备总时间 + 目标设备预测总时间`。其余情况下仍保留初筛、局部预测及独立经验场景，但不把已覆盖子集倍率外推为模型加速比，也不直接断言“亲和昇腾”。

## 手工校准

从算子详情复制签名，在高级配置中填写数组，例如：

```json
[{"signature":"从当前任务详情复制", "source_us":100, "target_us":80,
  "evidence":"同Shape、dtype、精度、Batch和软件条件下的双侧实测，记录文件及范围"}]
```

源/目标耗时必须属于可比较工作量。校准会应用到当前范围内同逻辑算子、输入 Shape/dtype 签名的调用；签名不包含完整调用栈，路径差异必须人工核验。过期或重复签名被拒绝。校准优先于解析模型，不把用户输入伪装为自动实测。

## 可追溯性与安全边界

结果保存硬件/平台版本快照、假设、输入 SHA256、引擎摘要、事件归属和时间守恒审计。修改规格不会影响历史结果。单机同时运行一个隔离后台进程，忙时返回提示，不排队；默认超时 600 秒、RSS 软限制 4GiB。上传单文件默认 2GiB、解压/CSV默认 4GiB、Trace 200 万事件、选中活动 20 万条；空间软配额 10GiB。网页显示服务端实际限制。

大文件可根据本机可用内存调整后重启服务，例如：

```powershell
workload_modeler/.venv/Scripts/python -m workload_modeler --port 8770 --upload-limit-mb 4096 --expanded-limit-mb 8192 --memory-mb 16384 --timeout 1800
```

参数容量单位为 MiB。上传采用流式落盘；JSON解析仍可能消耗远高于文件体积的内存。上传成功不代表可在内存或事件数限制内解析；优先使用 `.json.gz` 降低上传体积，必要时缩小原始采集范围。预检查会读取完整Trace，选择单个Step不会降低预检查阶段的内存需求。

服务供可信本机或局域网共享使用，阻止跨站写入，不执行上传代码。Worker 并非操作系统安全沙箱。任务崩溃详情见对应目录 `worker.log`；重启后未完成任务标为失败，请复用输入。任务列表按名称搜索、每页50项；API支持offset/limit分页（默认200项，不等于总数上限）。结果查询为首版内存加载方案，不适合海量任务服务。
